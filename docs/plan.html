homebridge-eufy-clean

Implementation plan for exposing the Eufy Clean L60 to Apple Home through Homebridge 2. 2026-09-17.

1. Two corrections to the earlier discussion

The L60 is not T2190. In eufy-clean's device table T2190 is the RoboVac L70 Hybrid. The L60 family is T2267 (L60), T2268 (L60 Hybrid), T2277 (L60 SES) and T2278 (L60 Hybrid SES). "L60 ES" is almost certainly the self-empty-station variant, T2277 or T2278. Phase 0 confirms the exact code from the account's device list.
Local Tuya control does not work for the L60. Every existing RoboVac Homebridge plugin, including the maintained hov3rcraft fork, states that the L60 is unsupported because its messages are "encrypted". They are not encrypted. They are protobuf blobs, base64-encoded, carried inside Tuya data points (the "novel API"). The only working open implementation, eufy-clean, drives these devices over Eufy's own AWS IoT MQTT broker using per-account client certificates obtained at login. So the config is email + password, not deviceId + localKey + IP. A DHCP reservation is irrelevant. Control goes via Eufy's cloud, but it is push-based, so latency is fine.

The rest of the earlier proposal holds. Homebridge 2 has a real Matter API. The Roborock Matter plugin (homebridge-roborock-matter-vacuum) uses it to publish a native Robotic Vacuum Cleaner with run mode, clean mode, operational state, power source and Service Area, and is a direct template for the HomeKit side.

2. Architecture

Three layers, each testable alone. The protocol layer knows nothing about Homebridge. The Homebridge layer knows nothing about protobuf. EufyVacuum in the middle holds a typed, normalised state object and emits change events; the Matter adapter subscribes to it.

3. Protocol facts (from eufy-clean source)

ConcernHow it works
LoginHTTPS to Eufy's home API with email + password + a random openudid. Returns a session and an MQTT credential bundle: broker endpoint, thing_name, client certificate PEM, private key, user_id, app_name.
Device listEufy "devicerelation" API, with a fallback that synthesises entries from the cloud device list. Each entry carries device_sn, model code and a current dps snapshot.
Transportmqtt:// to the AWS IoT endpoint with cert + key. Subscribe cmd/eufy_home/{model}/{sn}/res and smart/mb/in/{sn}. Publish to the /req and smart/mb/out/{sn} counterparts.
Message envelopeJSON with a head (client id, cmd 65537, version 1.0.0.1) and a stringified payload containing { account_id, device_sn, protocol: 2, t, data: { dps... } }.
Novel DPS map152 play/pause (control), 153 work status, 154 clean params, 158 clean speed, 160 find robot, 163 battery, 167 statistics, 168 accessories, 173 go home, 177 error code.
CommandsAll control is ModeCtrlRequest from control.proto, encoded and written to dp 152: START_AUTO_CLEAN, PAUSE_TASK, RESUME_TASK, STOP_TASK, START_GOHOME, START_SPOT_CLEAN, START_SELECT_ROOMS_CLEAN, START_SCENE_CLEAN.
Statedp 153 decodes to WorkStatus (state enum plus mode). dp 177 decodes to ErrorCode. dp 163 is a plain integer. Clean speed lives inside CleanParamResponse on newer firmware, with dp 158 as fallback.
Roomseufy-clean sends START_SELECT_ROOMS_CLEAN with no room list, so room-targeted cleaning is unproven. control.proto and map_manage.proto/multi_maps.proto exist, so the fields are there to be tried. Scene clean by index is proven and is the fallback for "clean the kitchen".

Depend on eufy-clean or vendor it?

Recommendation: vendor a lean client. eufy-clean pulls in tuyapi from a git URL, node-rsa, got, is, randomatic and logs with bare console.log, and its state layer is untyped. What we actually need is one 340-line login file, the MQTT connector, protobufjs, and six .proto files. Its licence is permissive with attribution and a requirement to mark modifications, so copy the protos and login logic into src/eufy/ with a NOTICE file. Homebridge plugin quality depends on clean reconnect and typed state, which is easier to own than to wrap.

5. Phases

PhaseDeliverableDetailDone when
0scripts/discover.ts run with bun against the real L60 Login, print model code and whether the device is MQTT + novel API. Dump raw dps. Decode 153 and 177. Subscribe and print live updates. Send START_GOHOME, then RESUME_TASK. Attempt to read the map and room list. Everything later depends on what this prints. L60 docks on command. We know the model code, the WorkStatus enum values it emits, and whether room IDs are readable.
1src/eufy/ client + unit tests Port login + MQTT from eufy-clean with proper types, a logger interface instead of console, exponential reconnect, and credential refresh on auth failure. Codec loads protos once. EufyVacuum exposes state (status, battery, charging, error, speed) and commands (start, pause, resume, stop, dock, locate, setSpeed, cleanRooms, cleanScene). Tests cover codec round-trips and dps to state mapping using fixtures captured in Phase 0. A 20-line script drives the vacuum through the client. Tests green.
2Homebridge platform + Matter accessory Platform logs in, discovers, registers one RoboticVacuumCleaner per device via api.matter.registerPlatformAccessories. Clusters: rvcRunMode (Idle, Cleaning), rvcCleanMode (Quiet, Standard, Turbo, Max), rvcOperationalState (Stopped, Running, Paused, Docked, Charging, Error), powerSource (battery %, charging), identify (find robot). Handlers call EufyVacuum, apply optimistic state, and reconcile on the next MQTT push. Mirror the Roborock plugin's structure. Vacuum appears in Apple Home with the native icon. Start, pause, dock, battery and Siri "start the vacuum" work.
3Rooms If Phase 0 proved room IDs: Service Area cluster with supportedAreas from the map and selectAreas handler that sends START_SELECT_ROOMS_CLEAN with those IDs. If not: configured rooms map to scene indices and drive START_SCENE_CLEAN. Room selection in Apple Home starts the right room. Siri phrase works.
4Hardening + release Refuse to start with a clear log line if Matter is not enabled. Stale accessory cleanup. config.schema.json. README with Matter enablement steps. Publish to npm and submit for Homebridge verified plugin listing later. Installed on the home server from npm, survives a Homebridge restart and an overnight run.

6. Risks and unknowns

  • Room-targeted cleaning is unproven. eufy-clean only sends the bare START_SELECT_ROOMS_CLEAN. If the L60 needs a room list in the request and the map protos do not yield IDs, rooms fall back to scenes created in the Eufy app. Scenes are proven.
  • Cloud dependency. No internet, no control. Eufy has also broken the MQTT list endpoint before, which is why eufy-clean carries a fallback. We inherit that fragility and should surface it clearly in logs rather than crash.
  • Account region. Login endpoints differ by region. eufy-clean tries EU then US for Tuya; the MQTT path uses a single domain. Verify in Phase 0.
  • Homebridge 2 Matter API surface. Documentation is thin. The Roborock plugin is the working reference and is actively maintained against it.
  • Two clients on one account. Running the plugin and the Eufy phone app at once is fine; eufy-clean and Home Assistant users do it. The plugin uses a distinct openudid.

7. Questions to settle before Phase 0

  • Server: Node LTS, no Homebridge yet. Decision: fresh Homebridge 2, plugin on a child bridge with Matter enabled. No HAP fallback.
  • Are rooms already named and a couple of scenes defined in the Eufy app? Phase 0 uses them to test room and scene cleaning.

8. Tooling

  • Bun for scripts and tests, tsc for the published build (Homebridge loads CommonJS from dist/).
  • Zod schema for config, with the TypeScript type inferred from it.
  • protobufjs with the .proto files loaded at runtime (same approach as eufy-clean) rather than generated static code. Keeps the codec small and the protos editable during discovery.
  • Vitest for codec and state-mapping tests using captured fixtures. No tests for Homebridge wiring.
